# PDF 协议差异对比工具

这个小工具用于把“旧协议 PDF”和“新协议 PDF”按章节/小节抽取出来，自动输出差异报告。它适合日常协议更新审阅：先告诉你新协议相对旧协议在哪一章、哪一节发生了新增、删除或修改，再给出关键片段，帮助你快速定位到 PDF 原文复核。

桌面界面中的全部按钮、页面范围、高级参数和 HTML 报告阅读方法，见[《文件对比工具使用说明书》](docs/文件对比工具使用说明书.html)。

桌面默认比较路径已使用原生字词、字体、位置和区域归属证据，并保留不确定结果。修复范围与验收证据见[正式路径验收记录](docs/verification/stable-closeout-20260908.md)。Docling 等重型解析器仍是独立评估候选，研究过程见[通用引擎第一阶段记录](docs/verification/general-engine-evaluation-20260907.md)；候选测试不代表整份报告准确性通过。

## 长文档进度与终止

运行桌面入口 `.venv/bin/python gui_app.py`，选择两份 PDF 后开始比较。运行时会显示预扫描、读取、章节匹配和报告生成等阶段；页数或候选数是当前阶段的进度，不是整项任务的完成百分比。

需要停止时点击“终止比较”。界面会先显示“正在停止”，结束本次比较及其 OCR 子进程，清理本次临时文件后恢复“开始比较”。运行时关闭窗口也会先停止任务，完成清理再关闭。若系统暂时无法结束后台进程，界面会显示清理错误并继续重试，期间不会启动第二个任务。

只有完整生成的报告才会发布到输出目录。取消不会覆盖或删除以前的报告。每次表格 OCR 最多等待 60 秒；超时会保留失败说明及已有截图/表格证据，不能把未识别内容视为没有差异。

## 能输出什么

每次运行会在 `results/protocol_diff_时间戳/` 下生成：

- `protocol_diff_report.html`：最直观的浏览器版报告，包含左侧差异导航、红绿高亮、旧/新片段并排对比。
- `protocol_diff_report.md`：Markdown 版报告，便于放进文档系统或代码仓库。
- `protocol_diff_report.txt`：纯文本版本，便于复制到邮件、IM 或审阅记录。
- `changes.csv`：正文/章节差异表，可以用 Excel 打开筛选。
- `table_changes.csv`：表格行变化表，包含旧/新表题、页码、配对分数、参数和值。
- `protocol_diff_data.json`：机器可读结果，包含正文差异、表格配对与完整行变化、公式版面隔离元数据、视觉漏检核对项、章节位置和抽取元数据。

表格内容会按 PDF 中实际观察到的表头整理成行级记录；没有可信表头时只使用
`Column 1 / Column 2 / ...` 这类中性列名，不会仅凭列数猜成某一种电气参数表。
HTML 只展示确有行级变化、表题/表号变化或单侧新增/删除的表格，并列出旧/新表题、页码、配对相似度和截图；
正文变化先列出具体文字片段变化和旧/新上下文，再显示并排的源 PDF 截图。带符号的小数和科学计数写法按完整原文显示；它们仍是文字变化，不代表工具已解释参数含义。只有实际源词能唯一定位时才提供“定位对应原文”，点击后同时显示旧/新局部截图；来源不完整或重复时明确提示定位未确定。完整条件与单位保留，特殊字形和公式版面沿用复核提示。首屏正文显示5条明细，其余全部可展开；表格行明细先于截图，超过20行仍可展开查看。淡红/淡绿底色只覆盖已有证据支持的变化词，相同文字不着色，页边行号、章节标题、Table、Figure 和显示公式区域不进入正文标色；
公式自动对比已关闭。分式、根号、上下标、式号和编号显示公式只用于版面隔离，不生成公式增删、修改、相似度或颜色差分结论；报告写入边界还会丢弃旧调用方注入的遗留公式变化，避免绕过禁比规则。公式周围可可靠抽取的普通说明文字仍按正文比较，`Equation 30-3` 这类引用也保留为可回源定位的信息；
可抽取文字完全一致且页身份可唯一证明的页面，还会执行低分辨率源像素核对。仅含 Section/Table/Condition 等引用定位编号变化的页面虽可唯一配对，但当前抽取证据只有整行边界框、没有逐字符编号坐标；工具不会屏蔽整行后认证一致，而是把该页记录为视觉覆盖未完成，避免吞掉同一行内的真实小图形。若两版文字块发生整体移动、换行或重排，当前阶段同样不猜测页面配准，也不会把整页位移伪装成图形变化卡。其余可直接对齐页面若存在图片、印章或普通矢量图变化，而正文和表格层没有解释该变化，报告会新增“视觉漏检核对”卡，显示旧页、新页和局部差异掩膜。抽取层已用坐标证明并过滤的页眉、页脚、页边噪声，以及已有表格/公式隔离区域不会重复报警。视觉渲染快照的 SHA-256 必须与文字抽取快照一致；重复页无法唯一配对、后端缺失或任一页失败都会阻止“无差异”结论。该卡只阻止假一致，不会把像素猜成技术文字；
HTML、Markdown、TXT 不展示作者、邮箱、版权、修订历史等文档元信息，也不重复展示已由完整表格截图覆盖的线性化表体；表体去重会绑定原页和 occurrence 数量，混在表体末尾的正常规范句仍单独保留。这些原始事实继续完整保留在 JSON/CSV 审计文件中；
Table、Figure、Formula 和正文采用互斥的视觉证据所有权：Table 由专用表格卡和行级结构化比较负责，不再重复进入正文截图；Figure 在报告末尾的“补充原图”折叠区按全文图题和文档顺序进行单调配对，只并列显示旧版/新版原图，不对图内标签做文字或颜色自动比较；Formula 区域只隔离，不参与任何自动差分。Figure 裁剪以下一个正文段落、章节、表格、公式、图题或坐标确认的页脚为边界；普通正文中提到 Figure 的引用句仍按文字比较。若源图渲染、快照校验或裁剪失败，图内文字保持在读者差异中，不能静默消失。原始抽取和 JSON 审计事实始终不变；
已判定未变化的表格不会占用导航和报告篇幅。报告还保留字符、表格、像素及覆盖不足等复核项；补充配图只提供上下文，不等于已确认变化。像素核对卡的编号按钮用于跳转原图区域，框内可能包含未变化像素，不推断技术含义。

HTML 顶部的“审阅队列”把每个可处理事项分为“内容变化”“待核实”和“未完成核对”，默认只显示已检测到的内容变化；每项都能跳到对应正文、表格、视觉页或覆盖清单。三类事项的计数单位不同，不能相加为技术变化总数。视觉页证据和页内像素区域默认折叠、按需加载，原始区域和掩膜仍完整保留；“已阅/需跟进”只保存在当前浏览器，不会改变 HTML、JSON 或比较结论。正文中较短但含数值、正负号、比较符、否定或规范性情态词的变化也会优先保留一页一侧的源图定位，普通短文字变化不会因此批量增加截图。
跨页表格会容忍抽取器在某一版本多识别出的冗余父章节编号；跨小节续表还必须共享较深的数字章节前缀，不能只凭相邻页和同名表题合并。唯一出现且表号、表题完全相同的表可以跨越章节定位漂移；表号改变时，则需要至少两张唯一描述性表题共同证明一致的编号偏移，才允许跨章节候选配对。若同一表从中性 `Column N` 表头变为明确的 Parameter/Symbol/Value/Unit 表头，只有所有单元格按顺序等价时才抑制版式误报，真实数值或附注变化仍保留。
无表题、所有非空行都落在同一物理列且以 `Note:`/`Notes:` 开始的带框说明块仍作为普通正文比较，不生成伪表格截图；明确表题优先保留。Figure 内部文字只有在当前变化卡的同一侧已经生成坐标支持的 Figure 原图时才退出读者文字流；缺少原图时按正文保留，不能靠 `MCB`、`Reference`、`VMA` 等术语词表删除。

## 安装

在本项目目录运行：

```bash
python3 -m pip install -r requirements.txt
```

复杂多栏页面需要额外验证时，可选安装 Docling 版面后端；它不是默认依赖，也不会
拖慢普通 PDF 的默认处理路径：

```bash
python3 -m pip install -e '.[layout]'
```

如果 PyCharm 当前解释器是 `/Users/mac/anaconda3`，请用同一个解释器安装依赖：

```bash
/Users/mac/anaconda3/bin/python -m pip install -r requirements.txt
```

如果你是在 `/Users/mac/PycharmProjects/RinysProject` 根目录打开 PyCharm，
也可以在根目录运行 `python3 -m pip install -r requirements.txt`。根目录
依赖文件会把本工具以 editable package 安装进当前解释器，PyCharm 就能识别
`protocol_pdf_diff` 导入。

## PyCharm 直接运行

打开 `main.py`，只需要改顶部用户参数区：

```python
OLD_PDF_PATH = "/path/to/old.pdf"
NEW_PDF_PATH = "/path/to/new.pdf"
OLD_START_PAGE = None  # 例如 10；None 表示从第一页开始
OLD_END_PAGE = None    # 例如 25；None 表示到旧 PDF 最后一页
NEW_START_PAGE = None  # 新旧范围可以不同
NEW_END_PAGE = None
OUTPUT_DIR = "results"
OCR_LANGUAGE = None   # 中英扫描页可设为 "chi_sim+eng"
LAYOUT_BACKEND = "native"  # "native"（默认快速）、"auto" 或 "docling"
VISUAL_WATCHDOG = True      # 推荐保持开启；只增加未解释视觉变化的复核证据
```

然后运行：

```bash
python3 main.py
```

如果两个 PDF 路径留空，脚本会自动生成内置多页 demo PDF 并跑一遍。这个 demo 包含旧 4 页/新 5 页、页码漂移、重复页眉页脚、视觉图块变化、章节新增和正文修改，比最小样例更接近日常协议更新。
运行结束后优先打开终端打印出来的 `protocol_diff_report.html`，它比纯文本更适合快速看清“旧协议删了什么、新协议加了什么”。

## 命令行运行

```bash
python3 main.py --old-pdf /path/to/old.pdf --new-pdf /path/to/new.pdf
```

如果只想比较长 PDF 中的一段，可以给新旧 PDF 分别指定页码范围。页码是
PDF 阅读器常见的 1-based 页码，且包含起止页：

```bash
python3 main.py \
  --old-pdf /path/to/old.pdf --old-start-page 30 --old-end-page 45 \
  --new-pdf /path/to/new.pdf --new-start-page 34 --new-end-page 51
```

当旧、新两侧都完整指定起止页时，工具把这两个页窗视为用户声明的强关联范围：常规章节
匹配和结构证据仍优先使用；此后工具会对所有仍未配对、但具有唯一同题或真实步骤/段落骨架重合的技术章节进行全局单调配对，而不是只救回一对。
若页窗内已有其他技术章节配对，额外锚定必须还有真实的步骤/段落骨架重合，不会把完全无关的剩余章节强配；
若一对技术正文都没自动配出，用户的双侧页窗声明本身会授权最相关的一对作为最低限度的关系锚点。报告会明确标注“用户指定双侧页窗强关联”，
并继续显示实际全文相似度；其余没有对应内容的章节仍按新增或删除列出，修订历史等文档元数据不参与这项强配。只有一侧
指定页码、任一侧正文为空或抽取失败时，不会启用这项授权。

可选参数：

- `--output-dir results`：指定报告输出目录。
- `--demo`：强制生成并比较内置示例 PDF。
- `--old-start-page 30` / `--old-end-page 45`：只抽取旧协议指定页码范围。
- `--new-start-page 34` / `--new-end-page 51`：只抽取新协议指定页码范围。
- `--min-section-match-similarity 0.72`：章节被重命名/重编号时，仍判定为同一章节的最低相似度。调低会减少新增/删除，调高会减少误配。
- `--max-snippets 20`：每个章节的基础片段展示预算；完整章节仍参与比较。HTML会恢复已有完整审计片段，并将首屏之外的明细折叠保留；若调用方未提供完整片段，仍明确披露无法恢复的未展示数量。
- `--include-unchanged`：同时列出未变化章节。
- `--ocr-language chi_sim+eng`：指定扫描页 OCR 语言；需要系统已安装对应 Tesseract 语言包。
- `--layout-backend native`：默认快速路径，不导入或运行 Docling。设为 `auto` 或
  `docling` 后，仅当原生坐标已经判定页面存在阅读顺序风险时，才会尝试可选的
  Docling。候选必须与原生页面逐字符完全相同才会采用；即使 token、整行或整段集合相同，
  只要顺序改变也会回退原生结果，因为当前还不能端到端证明技术值、enabled/disabled 状态
  与 Mode/Condition 所有者仍保持绑定。这个后端目前只提供保守的第二解析器一致性审计，
  不宣称修复复杂多栏阅读顺序。
  它不会因第二解析器一致而提升可靠性状态。`docling` 未安装时会提示安装命令，
  `auto` 则保留原生结果。转换范围会收紧到风险页最小连续页窗；建议先对有代表性的
  复杂页窗验收，再用于批量任务。
- `--no-visual-watchdog`：关闭文字一致页的像素漏检核对，仅建议在处理时间排障时使用。
  默认开启；页面插入或换序导致页码移动时，会按两侧唯一出现且完全相同的页面文字配对。两侧
  同页都没有文字层且选择页数相同时，也会保守按同页核对，但整体可信度仍是“无法判断”。
  显式关闭、后端不可用、源哈希不一致或有歧义/失败页时，本次结果不会允许“无差异”结论。

旧版脚本中的 `--unchanged-similarity` 仍可传入以保持启动兼容，但当前不参与判定。词尾、单复数、大小写技术标识符、否定、数值和比较符变化都会保留，避免用相似度猜测语义等价。

## 识别逻辑和边界

每份报告最上方、命令行结束提示和桌面界面都会先显示本次识别可信度：

- `可靠`：两份文档都落在当前支持范围内，视觉哨兵已完整核对所有可唯一配对的候选页，并且没有语义层未解释的视觉变化；只有此状态下，才可以自动得出“未检出受支持的可抽取文字、结构化表格或视觉漏检证据”。公式本体不属于自动判等范围。
- `需人工复核`：仍会保留抽取到的正文和表格证据，但存在多栏、表单、按页回退、文字过少或单字碎裂等风险；零变化不能证明一致。
- `无法判断`：至少一侧缺少可比较文字或章节，常见于未安装 Tesseract 或 OCR 仍未识别到文字的扫描件；报告会明确写“无法判断是否存在差异”。

这三个状态只评价本次抽取和结构识别是否足以支撑结论，不会为了提高状态而删除已经发现的变化。通用核心不按出版方、标准名称或某两份样例 PDF 改写正文；未知内容默认保留。只有抽取层提供的页边坐标、表格边界或完整空间水印簇等足够证据才能分离版面内容；单凭文字像“页眉”、跨页重复或 token 重合都不够。位于顶部窄区域且在绝大多数选定页重复的运行页眉会从正文流分离，避免污染章节和表格配对，但页眉原文仍作为独立比较单元：相同页眉不报，版本号、单位或技术标识变化会进入 HTML/Markdown/TXT 和 JSON/CSV。若 PDF 把视觉页脚插进正文文本流，工具会用多数页面同一页边的 `DocumentBlock` 坐标确认版权或草稿状态片段，只剥离已证明的页脚片段，保留同一抽取行中相邻的技术正文。

章节标题现在绑定到原生字词、字体和位置；同一水平行包含两栏时，只有实际栏间空隙才能建立两个独立标题来源。图注、表格、公式和正文保留各自区域归属。空白字符恢复需要 PDF 字体中的 CID/GID 和空轮廓证据，不按私用字符编号替换；缺少证据的字符原样保留。

未配对内容先核对两侧来源覆盖与尚未消费的相同内容。证据不足时显示“待核实原文”，不直接断言新增或删除，也不涂成确定的红绿差异。图、表目录按“条目编号、标题、出现次数”辅助配对，引导点和末尾页码只用于已证实的目录定位槽，标题中的参数仍参与比较。截图限制在相邻区域边界内，且不超过自身原始像素尺寸。

页面不能安全配对、文字块或坐标不兼容、图像读取失败时，报告顶部可展开“未核对页面及原因”，按旧、新 PDF 物理页码定位到源文件。没有差异卡不代表像素已确认相同；未核对页仍阻止自动一致性结论，JSON 保留逐页原因与类别。

页脚分离保留完整原文审计；只有位于页边、与文字团簇明显分开的实际页码词才从页脚比较值去除。句末数值、出版版本号和不同页面上的版本出现次数均继续比较。页眉或 logo 的像素变化仍可能显示为技术复核项，不能据此认定协议正文发生修改。

同一 SHA-256 字节快照且选择页窗相同时，语义层固定为零正文、零表格、零公式变化；解析器自身的不稳定不能制造“同一文件发生修订”的假卡，抽取风险仍会保留在可信度说明中。普通编号章节下的完整叙述句列表要求严格连续和句子形态证据；页窗从 `N` 项开始时也可识别，但活动章节的真实下一编号优先保留，普通正文会立即结束列表链。该规则不依赖标准名称或技术关键词。`MCB`、`HCB`、`TP4a`、`scope`、`reference` 等短技术文本一律不凭词形猜成图示噪声；在获得真实图形区域归属证据前，读者层不会折叠这类标签。

当页面栅格图像覆盖大部分区域，且原生文字不足或字符坐标不能证明文字分布完整时，工具会在系统存在 Tesseract 的前提下自动尝试整页 OCR。重叠图像按实际并集计算覆盖率，避免重复 XObject 误触发；原生字符达到数量门槛并占据至少一半页面高度分段时不会重复 OCR，稀疏页眉/页脚或缺少字符坐标不能单独阻断 OCR。只要页面仍由大面积栅格图主导，就会保留风险警告并降级，防止不完整搜索文字层造成假一致。扫描页按 300 DPI 渲染，但会在分配位图前拒绝超过像素预算的异常大页面；Tesseract 单页识别阶段最多等待 60 秒。默认使用 Tesseract 的默认语言，也可通过 `OCR_LANGUAGE` 或 `--ocr-language` 指定 `chi_sim+eng` 等组合；桌面界面保持默认 OCR 策略，不暴露专业语言参数。OCR 成功后文字可以参与章节识别和差异定位，但对应页会记录在 `ocr_pages`，整次比较至少保持“需人工复核”，不会自动得出一致结论。

可用语言取决于本机 Tesseract 安装，可先运行 `tesseract --list-langs` 检查。配置语言不会下载模型；缺少语言包、超时或识别失败都会形成明确警告。开源项目调研、分层后端路线和下一阶段验收门见 [`sources/research_pdf_parsing_landscape_20260718.md`](sources/research_pdf_parsing_landscape_20260718.md)。

## 解析基准、页面路由与审计证据

“能跑出报告”不等于“各种 PDF 都解析正确”。除了 old/new 差异回归外，仓库提供
**extraction-only** 解析基准：它只检查一份 PDF 的文字 anchor、阅读顺序、OCR 是否实际
使用和质量状态，不能用 self-diff 的零变化掩盖抽取退化。先运行不含任何私有文件的受控
基准：

```bash
python3 tools/benchmark_pdf_parsing.py --controlled \
  --output-json sources/parsing_benchmark_baseline_20260718.json
```

它会在临时目录生成并清理五类小型 PDF：线性原生文字、真正纵向重叠的**纯正文**定位双栏、公式、无框
表格、以及英文栅格扫描页。纯正文双栏门要求完整左栏先于右栏；无框表门还固定参数、数值、单位和
行顺序。轻量路径遇到跨行重复的“数字 + 已知工程单位”双栏时会保留 PDF 的逐行顺序并标记阅读顺序风险，
不会猜测 column-major；扫描页固定检查 `3.3 V`、`25 PS` 与阅读顺序。扫描页在
Tesseract 存在时必须真实 OCR，否则仅该 optional case 记为 `skip`。`pass` 表示该 case
的解析门通过，**不**表示该页面已具备自动判等资格；输出中的 `state` 仍是保守质量评估。

截至 2026-07-18，本机执行 `tesseract --version` 得到 Tesseract **5.5.2**，
`tesseract --list-langs` 包含 `eng` 与 `chi_sim`；上述受控命令实际运行了非 mock 的英文
栅格 OCR，基线记录为 5 个 `pass`、0 个 `fail`、0 个 `skip`，见
[`sources/parsing_benchmark_baseline_20260718.json`](sources/parsing_benchmark_baseline_20260718.json)。
这只验证受控英文 anchor 的端到端调用，不是中文、低清扫描、公式图片或任意复杂文档的
OCR 准确率声明。

真实私有 PDF 另用严格 manifest（只存相对文件名）运行；示例中每个 case 都是 optional，
缺少文件会 `skip`，但已有文件的 anchor 或状态失败会使命令退出 1：

```bash
python3 tools/benchmark_pdf_parsing.py corpus/parsing_benchmark.example.json \
  --corpus-root /path/to/private/pdf-corpus \
  --output-json /tmp/pdf_parsing_real_benchmark.json
```

该 summary 只含不透明的 `case_index`（本机 manifest 数组中的 1-based 位置）、通过/失败/
跳过、质量状态、页数、OCR 页、告警数、字符数和耗时；不会保存 case id、description、anchor、
PDF 文件名/路径、正文、输入 hash、解析出的 corpus root 或临时报告路径。`--output-json` 会
覆盖你明确指定的位置，因此私有运行建议写到 `/tmp` 或已忽略目录。受控模式不能与
`--corpus-root` 组合，避免误将私有文件纳入该门禁。

每页还会记录一个互斥的解析路由，供报告 JSON 的 `assessment.*.parser_route_pages` 和
`extraction_audit` 审计：

| 路由 | 含义 |
|---|---|
| `native_text` | 普通线性原生文字页。 |
| `native_layout_risk` | 有原生文字，但坐标证据提示阅读顺序可能非线性。 |
| `ocr_fallback` | 整页 OCR 成功；OCR 事实优先于其他页面特征。 |
| `image_text_layer` | 图像主导但仍有搜索文字层；该文字层可能不完整。 |
| `unreadable_image` | 图像主导且没有有效文字层、也未成功 OCR。 |

`image_dominant` 与 `ocr_used` 是独立事实：前者为真时无论有无搜索文字层都不会升为
`reliable`，因此至少保持“需人工复核”；无可比较文字时仍可能是“无法判断”。内部
`DocumentBlock` 保存页码、边界框、类型、阅读顺序和来源引擎，目的是让后续版面后端能
逐页对照证据；这些 block 本身不代表 Docling、PaddleOCR 或其他重型后端已全面接入或
准确率已验收。当前轻量后端仍保留这些 blocks 的几何信息，但不会用它们对数值双栏
推断列优先顺序；需要可靠区分长标签表与测量型双栏正文时，应接入并单独验收可选版面后端。
从 1.4.0 起，Docling 可作为明确选择的保守二次解析候选：默认 `native` 不会加载它；
`auto` / `docling` 只处理已标记 `layout_risk` 的页面，且候选必须逐字符一致。token、行或
段落重排都失败关闭，避免 enabled/disabled 或相同数值在不同 Mode/Condition 下重新绑定；
在形成带所有者边界的版面单元并通过真实 Docling 全链路验收前，不把重排当作识别增强。
表格截图和坐标块仍由原生路径产生，不混用不同坐标系；
任何采用候选的页面仍保留 `native_layout_risk` 和“需人工复核”状态。
JSON 的 `provenance.effective_thresholds.layout_backend` 记录所选策略，逐页
`extraction_audit` 记录实际参与比较的文字来源、采用时的 Docling 版本和坐标已证明的视觉
噪声区域数量，便于复跑与审计。`provenance.visual_watchdog_run` 另记录视觉哨兵的计划/
完成/失败/歧义页数、屏蔽区域数和渲染快照哈希。
新的 `extraction_audit` 只写路由、风险标志和 block 数，绝不写
`PageText`/`DocumentBlock` 原文或边界框；现有差异报告正文仍是审阅产物，应按源文档的
保密要求保存。

工具会识别常见技术文档标题格式，例如 `Part I`、`Annex A`、`A.1`、`Chapter 2`、`Section 3`、`第一章`、`第2节`、`1`、`1.1`、`一、`、`(一)`。Part、Annex 或嵌入子文档中的本地编号可以重新从 `1` 开始；无法确定父级时会保留重复章节并把可信度降级，而不是静默删掉其中一组。如果 PDF 把编号和标题抽成两行，例如 `1` 下一行是 `适用范围`，工具会尝试合并为同一节标题。如果 PDF 没有明显标题，工具会退回到按页块和正文相似度比较，并在报告中明确提示该 fallback 状态。

对于带有连续编号操作步骤的测试规程，工具会结合父章节上下文，尽量把步骤保留在父章节正文里，而不是把每一步都误拆成独立章节。该判断依据标题层级和句子形态，不依赖某个标准名称。

默认比较不是“旧第 2 页对新第 2 页”这种硬对齐。只要识别到章节结构，工具会先按章节编号、标题和正文相似度匹配逻辑章节，页码只作为报告里的定位线索。新增内容导致后续页码整体后移时，同一章节仍会被匹配到一起；无标题 fallback 场景也会尽量通过正文相似度跨页匹配，而不是只看页号。

当你指定 `--old-start-page/--old-end-page` 或 `--new-start-page/--new-end-page`
时，工具会先只抽取各自范围内的文字，再做章节/正文相似度匹配；两侧起止页都完整给出
时还会启用上述用户页窗强关联。报告顶部会显示
源 PDF 总页数以及本次实际比较的“旧选择页 / 新选择页”，方便你确认没有把范围外
章节混进去。

PDF 不是天生适合结构化比对的格式，所以请留意这些限制：

- 扫描版或图片版 PDF 只在检测到大面积栅格页、且系统安装了 Tesseract 时自动尝试整页 OCR；否则仍需先在外部完成 OCR。
- 表格会额外生成截图证据；编号显示公式只作为互斥版面区域，不做自动公式差分。正文仍按可抽取文本比较；对于抽取文字完全一致且可可靠配对的页面，图片、普通矢量图、盖章等其它非文字视觉差异默认由页级像素哨兵追加人工复核证据，但不会自动解释其技术语义。
- 只有页边坐标或完整动态页码等足够证据时才过滤页眉页脚；手工提供或无坐标的文本会保守保留，可能带来额外可复核噪声。
- 普通空格、软连字符、零宽字符、PDF 抽取出来的部分断词与同方向箭头字形等无语义显示噪声会谨慎规整；技术标识符/变量的大小写、公式、单字母状态、全大写标识符、版本号、比较符和数值默认保留比较；普通句首大小写可视为格式差异。
- 纯文本换行本身不足以证明行末连字符是断词，也不足以证明 `1.` 与下一行 `0 V` 应拼成 `1.0 V`；没有字符坐标证据时会保留为可复核差异。
- `5×10^-6` 只有出现 `^`、真实上标或等价版面证据时才按指数记法解释；编号显示公式可用小字号与基线偏移证明 `f^{1.5}` / `SDD_{MTFmin}`，但 `5*10-6`、`2x100`、十六进制 `0x10` 和 `<-5` 等歧义写法不会被猜成特定公式。
- 英文数词只在明确计数语境（如 `seven waveforms`）下与数字等价；公式、函数实参、枚举、版本、型号、文件名和引号字面量保留原貌。
- 表格会优先用 `pdfplumber` 版面坐标和表格线提取成行级记录，并在 HTML 中展示旧/新表题、页码、配对分数和截图；完整变化同时写入 `table_changes.csv` 与 JSON。如果 PDF 表格没有清晰网格，仍可能退回为普通文本顺序。
- 轻量双栏重排只支持没有跨行重复“数字 + 已知工程单位”的纯正文。已知单位是有限词表和符号（如 `V`、`mV`、`ps`、`UI`、`dB`、`GHz`、`GT/s`，以及 `Volts`、`Picoseconds`），普通计数如 `1 item` 不会被误判为单位。数值双栏既可能是长标签表，也可能是测量型叙述；当前会保留 y-first 文本、标记 `layout_risk` 并降级，等待可选重型版面后端提供可验收的阅读顺序证据。
- 整页 OCR 和表格 OCR 都需要系统额外安装 Tesseract；未安装、识别为空或执行失败时会给出明确警告，不会静默伪装结果。
- 页眉页脚、复杂多栏排版可能导致文本顺序和肉眼看到的不完全一致。
- 相似度匹配用于处理重命名或重编号章节；如果协议中大量章节正文模板高度相似，建议调高 `--min-section-match-similarity` 后复跑。
- 自动报告用于快速定位差异，最终协议结论仍建议回到源 PDF 复核。

## Corpus v0 逐文档回归门

修改抽取、章节识别、表格配对或降噪启发式前后，建议再运行隐私安全的 Corpus v0：

```bash
python3 tools/validate_corpus.py corpus/manifest.example.json \
  --corpus-root /path/to/private/pdf-corpus \
  --require-executed \
  --output-json corpus/local/summary.json
```

manifest 只保存相对文件名；私有 PDF、local manifest、报告和哈希都不进入 Git。缺少 optional 私有文件会明确记为 `skip`；在探索模式下不会因此失败。发布或准确度认证应加 `--require-executed`：默认要求真实版本对实际执行，认证必跑 case 缺失、全部 case 跳过或任一逐文档门禁失败都会退出 1，简单 self-diff 不能替代真实版本对。

Corpus 门禁按文档检查可靠性状态、技术正文/表格变化上限和必须出现/必须忽略的锚点，不使用总体平均分。测试套件还会现场生成多种章节结构的 old/new PDF 并注入公式、否定词、标识符和限值变化；这些用例不可因私有文件缺失而跳过。当前可靠支持范围是原生可选文字、线性阅读顺序和稳定编号章节；OCR 扫描件可以提供降级的差异定位证据，视觉漏检哨兵也只能追加人工复核证据。扫描件、复杂多栏、表单、幻灯片、异常密集的单字/短碎片抽取及图形语义仍不属于可靠自动判等范围。完整 manifest、Gold Accuracy 事件标注规则、anchor 扩充规则和状态语义见 [`corpus/README.md`](corpus/README.md)。

Gold Accuracy 可用 `minimum_distinct_families` 要求多个经人工审阅的文档族。工具会自动排除
同源 SHA 的 self-diff，并把重复提交的同一 old/new 字节对只计一次；family 名还会规整大小写
和内部空白。`family` 本身仍是 manifest 维护者的受信声明，不能靠字符串从 PDF 中证明出版方
或标准归属。普通回归默认要求一个文档族；对外宣称跨标准通用性时应把门槛设为至少 `2`，
并提供非 OIF 的真实 old/new 人工完整标注版本对。动态合成样本和解析 benchmark 都不能替代
这个变化召回率证据。

桌面版现已支持逐页进度和终止比较；整页及表格 OCR 的单次识别上限均为 60 秒。
整份文档累计的 OCR 时间/页数预算尚未实现，单次超时不代表整份文档一定在固定时间内完成。
需要限制处理范围时仍可使用页窗。累计预算耗尽后列出未处理页并保持 `degraded` 或
`indeterminate` 的处理，属于后续工作。

## 桌面版 GUI

如果要给不熟悉命令行的同事使用，可以运行桌面界面：

```bash
python3 gui_app.py
```

界面支持：

- 选择旧协议 PDF、新协议 PDF 和报告输出目录。
- 分别填写旧 PDF 与新 PDF 的起始页/终止页；留空表示从开头或到结尾。
- 点击 `开始比较` 后生成 HTML、TXT、正文 CSV、表格变化 CSV 和 JSON 报告。
- 调整章节匹配阈值和每章展示片段数；界面不提供会隐藏细微内容变化的阈值。
- 扫描件沿用默认 OCR 策略；需要指定 `chi_sim+eng` 等语言组合时使用命令行 `--ocr-language`。
- 内置 demo 保留在命令行 `python3 main.py --demo`，桌面界面只保留真实旧版/新版 PDF 工作流。
- 比较完成后直接打开 HTML 报告或报告目录。

GUI 与命令行复用同一套比较逻辑，生成的报告格式也完全一致。

桌面界面由一份随程序打包的 HTML/CSS 驱动：macOS 使用系统 WKWebView，Windows 强制
使用 Edge WebView2。两端共享同一布局、颜色、玻璃卡片、状态动画和响应式规则；不会在
Windows 上退回旧版 IE/MSHTML。窄于 900px 时双文档卡自动纵向排列，底部状态和操作保持
可见。可用真实入口执行非交互 GUI 自检：

```bash
python3 main.py --gui-smoke-test
python3 gui_app.py --smoke-test
```

`main.py` 检查共享界面资源；`gui_app.py` 还会真实启动系统 WebView、读取计算后的背景和
动画样式再退出。Windows 自检同时确认实际内核是 WebView2。PyInstaller EXE 继续嵌入
`windows_dpi.manifest`，让 100%、125% 和 150% 缩放使用明确的 DPI awareness。

## 打包成无 Python 桌面程序

打包使用 PyInstaller。它不能跨系统编译：macOS 只能构建 macOS app，
Windows 需要在 Windows 机器上构建 `.exe`。

macOS 构建：

```bash
./build_macos.sh
```

产物：

```text
dist/ProtocolPdfDiff.app
```

Windows 构建：

```bat
build_windows.bat
```

产物：

```text
dist\ProtocolPdfDiff.exe
```

如果想手动执行，也可以在目标系统运行：

```bash
python -m pip install -r requirements.txt
python -m pip install -r requirements-build.txt
python build_desktop.py --clean --onefile
```

生成后的 app/exe 已包含 Python、pywebview、共享界面、pdfplumber、表格截图依赖和本项目代码，
普通用户不需要单独安装 Python。Windows 11 以及大多数已更新的 Windows 10 已带 WebView2；
若运行时缺失，程序会明确提示安装 Microsoft Edge WebView2 Evergreen Runtime，不会改用另一套
渲染器。macOS 未签名 app 第一次打开时可能需要在 Finder 中右键选择
“打开”；Windows 未签名 exe 可能会触发 SmartScreen，需要按公司内部软件分发流程处理。

如果没有 Windows 开发机，可以在 GitHub Actions 里触发 `Build desktop apps`
工作流。它会在 Windows runner 上生成 onedir EXE、真实启动 Edge WebView2、保存
renderer probe 与 Windows 原生窗口截图，并上传 `ProtocolPdfDiff-windows-latest`
artifact。下载后包含 `dist/ProtocolPdfDiff/ProtocolPdfDiff.exe` 及其依赖和相应验收证据。
本地 `build_windows.bat` 仍生成便于分发的单文件 EXE；两种打包方式使用完全相同的
HTML/CSS 和 WebView2 后端。
